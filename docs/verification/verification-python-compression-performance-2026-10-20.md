# Python compression performance slice — 20 October 2026

This records the selected owning native-codec/compression workload on baseline
`0928053389fcf237e53f682442510ae19ef5eb5c` plus the uncommitted **2.14.0** changes.
The actual compiler reports schema language **1.20.0**. It generated and imported
the benchmark model through the normal Python backend. This measurement adds no
schema, language or public API changes.

The host ran Windows 11 build 26300, CPython **3.14.3** x64, zlib
**1.3.1.zlib-ng**, stdlib Zstandard **1.5.7**, and python-lz4 **4.4.5** linked to
liblz4 **1.9.4**. Generated-SDK qualification was active concurrently. These timings
were not collected on an isolated host and establish no performance pass threshold,
earlier-compiler regression result or general provider speed ranking.

## Reproduction and retained evidence

Run the tracked [benchmark script](../../qualification/python_compression_benchmark.py)
after building the compiler and making the selected optional providers available:

```powershell
python -B qualification/python_compression_benchmark.py `
  --compiler out/build/opc-implementation/serializer.exe `
  --build out/build/backlog-2026-10-20/python-compression-benchmark `
  --provider-path out/python-compression-provider `
  --output out/build/backlog-2026-10-20/python-compression-benchmark.json
```

The optional local provider directory contains pinned `lz4==4.4.5`; it does not
modify the global Python installation. Omit `--provider-path` when the desired
provider is already on the interpreter's search path. The JSON records actual
available/unavailable formats, SDK/provider versions, CPU/platform description,
five individual timings per operation, medians, allocation samples, limits,
payload hashes and generated-source size/hash. Its retained local path is
`out/build/backlog-2026-10-20/python-compression-benchmark.json`.

The final lifecycle helper was measured through the captured compiler in
`out/build/backlog-2026-10-20/kotlin-compiler-4a4f8604/`, SHA-256
`4a4f8604bb76361f2e5f33e20e1b7e5176d6916a1b3ed56d98f7b79675d8d813`.
The canonical invocation above produces the same Python profile after building
that source; the captured executable avoided concurrent compiler replacement.
The refreshed command output is retained as `python-compression-benchmark-final.log`.

Each workload contains **1,048,576 payload bytes** in an owning generated
`array uint8`, alongside a `uint64` sequence. One repeats a fixed textual pattern;
the other uses `random.Random(6000292553122662746).randbytes(...)`. Both produce
**1,048,587 serialized bytes** with `BINARY_NONE`. The script checks native model
round trips and exchanges each standard compressed frame with an independent
provider-native API before measuring it.

Every timed operation has one warmup and **five measured iterations**, with
`perf_counter_ns` tracing disabled. Reported throughput uses complete serialized
MiB, including for decompression; it excludes model serialization from compression
timings. Native model encode/decode are measured separately. The provider baseline
uses compatible valid single-frame profiles at the same levels/checksum choices;
it omits the helper's byte admission, cancellation and exact-EOF checks. Identity
baselines make an explicit `memoryview(...).tobytes()` copy. There is no earlier
compiler or generated-source-size baseline.

Both byte directions allow 2 MiB, the decode window allows 8 MiB, and native
limits allow 2 MiB input and 2,097,152 collection entries. The complete generated
module occupies **54,799 bytes**, including the final callback/reentry-fencing
support helpers. Its SHA-256 is
`0258cd157cc4703fdbc34eb9a7b370c8ed63342c4241852030a4948d413eb1d4`.

| Format | Repeated compressed bytes | Random compressed bytes | Repeated encode/decode MiB/s | Random encode/decode MiB/s |

| Identity | 1,048,587 | 1,048,587 | 641.8 / 1,900.4 | 436.6 / 1,510.6 |

| zlib | 3,138 | 1,048,918 | 464.8 / 352.2 | 6.8 / 207.7 |
| Raw DEFLATE | 3,132 | 1,048,912 | 506.6 / 330.1 | 8.3 / 110.5 |

Across these samples, helper/provider-baseline throughput ratios range from
**0.32–0.97** for encoding and **0.13–1.12** for decoding. Baseline policy differences
and concurrent machine activity prevent attributing those differences to one
implementation detail. Native generated byte-array encode medians were
**0.78–1.24 MiB/s**; decode medians were **0.42–0.47 MiB/s**.

## Allocation measurement and remaining scope

Each operation also has one separate `tracemalloc` sample after `gc.collect()`.
Tracing begins after fixture/input creation and retains the returned result until
the peak is sampled. Helper encoding/decoding peaks range from **67,896 to
2,271,556 traced bytes** across the recorded workloads/formats. Native generated
encoding peaks at **2,134,043 traced bytes**; native owning decode peaks at
**8,450,530 traced bytes**. Raw per-operation samples and provider baselines remain
in the JSON.

These are traced Python allocations. They exclude preexisting inputs, do not
measure complete provider-native workspace or process RSS, and do not establish
a hard heap bound. Logical byte/window admission remains distinct from total
memory, decoded object storage and allocator overhead.

This is a selected compression/native-codec CPU, allocation and size slice for
`PY-Q05`, `PY-Q06` and `PY-Q07`. Their full language/XML workloads remain open,
along with other host/provider combinations, independent reproducibility replay
and broader performance qualification. Compression correctness and the selected
`PY-Z01`–`PY-Z10` checks are recorded separately in the
[implementation record](verification-backlog-2026-10-20.md).
